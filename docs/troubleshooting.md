# Troubleshooting

**Problem:** most of this tool's failure modes were found the hard way —
during real use, not in a test suite — and each one had a specific,
non-obvious cause. This page is the symptom → cause → fix table for the
incidents that actually happened, so the next person (including future you)
doesn't have to re-diagnose them from scratch.

## Symptom → cause → fix

| Symptom | Cause | Fix |
|---|---|---|
| `declare: -A: invalid option` (or similar) the instant you run *any* `claude-session` command | You're on stock macOS bash (3.2.57). Associative arrays (`declare -A`) require bash 4+, and several are declared at top level — they run before any argument is even parsed, so this crashes before dispatch on every subcommand, not just some. | Install a current bash: `brew install bash`. See [platforms.md](platforms.md). |
| `claude-session: cannot find its library directory` (or the tool silently fails to source its helpers) | The entrypoint resolves `share/claude-helpers/` relative to `bin/claude-session`'s own, symlink-followed location (trying `../share/claude-helpers` then `../lib`); if it was moved, partially installed, or `CLAUDE_HELPERS_LIB` points somewhere stale, that resolution fails. | Reinstall (`./install.sh`), or set `CLAUDE_HELPERS_LIB` explicitly to the correct `share/claude-helpers` directory. |
| Every session in `claude-session ls`/`doctor` shows as stale/dead (`✕` glyph) even though `claude` is clearly running | The liveness check used to test for `/proc/$pid`, which doesn't exist on macOS — every check reads as "process not found," so every card renders with the dead-session glyph, `doctor`'s stale-file check fires for everything, and the "waiting" stall check never fires at all (it's gated on the same alive check). | Fixed via `compat.sh`'s portable `kill -0 "$pid"` liveness check, which needs no `/proc` and works identically on both platforms. If you still see this, you're on an old checkout — update. |
| A session for a project whose name has a `.` or `:` in it (e.g. `my.project`) starts fine but can never be attached — `tmux: can't find window` | tmux silently rewrites `.` and `:` to `_` in stored session names but treats those same characters as window/pane separators inside a `-t` target string. A project name containing them creates the session under one internal name but every subsequent `-t` lookup for the literal name fails to match. | `claude-session` sanitizes project names the same way before building the session name (`PROJECT//[.:]/_`), so this only bites an old checkout or a manual `tmux -t` command typed with the raw name. Use the sanitized form (`my_project`), or update. |
| `claude-session schedule ...` fails with "command not found" for `systemctl`/`journalctl`, or the scheduler seems entirely unavailable | The scheduler backend is systemd-user-timers only in this release; there is no `launchd` backend yet, and no fallback is implemented. This is expected on macOS today, not a bug. | See [scheduler.md](scheduler.md) and [platforms.md](platforms.md). No workaround exists yet short of running the scheduled command another way (`cron`, a manual `launchd` plist) outside `claude-session`. |
| CPU usage on the host climbs and stays high for hours with no interactive Claude session running | Killing a `tmux` session or a `claude` process does not kill its children — they get reparented to init (`ppid=1`) and never stop on their own. A batch of killed sessions once left several `plugin:build` and `npm run dev` process trees running unattended for hours, driving sustained CPU load, invisible in `claude-session ls` because none of that shows up in Claude's own session-state files. | Run `claude-session doctor` — it scans the process table directly (not just Claude session state) and lists exactly this pattern under "orphaned dev process(es)." Clean them up with `claude-session doctor --reap` (interactive confirm, or `--force` for unattended use). See [doctor-orphans.md](doctor-orphans.md). |
| `doctor --reap` skipped a process you expected it to kill | The orphan wasn't actually dead weight: `doctor` walks the orphan's entire descendant subtree before reaping, and this one had real work running several levels down (an active `codex exec`, a test suite, a build) even though the root pid itself read 0% CPU. **An orphan at 0% CPU can still be holding an active job** — `--reap` deliberately skips anything its subtree scan classifies as active, since a false "idle" would silently destroy real work, while a false "active" only costs a delayed reap. | This is working as intended, not a bug. Check the "active: ... — reap will skip it" line `doctor` prints for that pid to see what it found running; re-run `--reap` once that job finishes. See [doctor-orphans.md](doctor-orphans.md#orphan--dead-weight). |
| A manual process count (`pgrep -f pattern \| wc -l` or `ps aux \| grep pattern \| wc -l`) is consistently one higher than expected | `ps | grep pattern` always matches its own `grep pattern` invocation — the full command line it's scanning includes the search string, so `ps aux | grep claude` matches itself. `pgrep -f` does **not** have this problem — `pgrep` excludes its own pid from its results — but it can still overcount when some *other* process's full argv happens to contain the pattern text, e.g. a `bash -c '...pattern...'` wrapper (a tmux pane command, a cron entry, an `eval` string) where the literal pattern sits in the wrapper's own command line, not just the target process's. This is a general shell gotcha, not specific to this tool, but it bites anyone hand-verifying `doctor`'s orphan counts. | For `ps | grep`, use the bracket trick: `ps aux | grep '[c]laude'` — the character class means the regex itself no longer contains the literal string `claude`, so grep can't match its own invocation. `pgrep -f` doesn't need that trick for its own process, but double-check any suspect pid (`ps -o args= -p <pid>`) before trusting a raw count if a wrapper could be in play. Simplest: trust `claude-session doctor`'s own count — it walks the whole process table structurally via `ps` (through `compat.sh`'s `_proc_table`), matching on real relationships like `ppid=1`, not by grepping for a pattern, so it has neither hazard. |

## Getting more detail

- `claude-session --version` prints the wrapper's own version, platform,
  bash version, and resolved library directory — the first thing worth
  checking (and the first thing to include) when something looks wrong.
- `claude-session doctor` is safe to run at any time — it only reads state
  and only mutates anything when `--reap` is explicitly passed.
- If a bug doesn't match anything above, it's worth checking whether it's
  platform-specific first: rerun with `CLAUDE_COMPAT_OS=linux` or
  `CLAUDE_COMPAT_OS=darwin` set explicitly to see whether the compat layer's
  platform detection is the actual culprit.
